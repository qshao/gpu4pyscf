# LCC benchmark plan: P100, V100, A100 (CPU vs original GPU vs new GPU), many QM job types

**Status:** proposed plan (revision 2: adds the QM job families). Nothing in sections 5-9 has been executed. Section 2 lists what the earlier exploratory runs on LCC established.
**Scope decision:** H200 excluded (queue pressure). Extends `2026-10-18-broad-qm-benchmark.md`; that plan's accuracy gates, timing protocol and audit rules still apply unless stated here.

## 1. Questions

1. **Accuracy.** Does the new GPU code (G1) reproduce independent CPU PySCF to the declared gate for every job type on every card?
2. **Speed.** How do CPU (whole 48-core node), original GPU (G0) and G1 compare, per card, size, method and job type?
3. **Memory.** How much GPU memory do G0 and G1 need, and what do the host-RAM and disk tiers cost in time?
4. **Capacity.** What is the largest system each card completes with G0 and with G1, per storage tier? (Main interest: small-memory cards.)
5. **Regime.** How do answers change with the contraction engine (cuTENSOR vs CuPy fallback)?
6. **Reach.** Which job types does G1 change at all? G1 touches DF integral storage, J/K, the DF gradient and XC code, so job types that do not use those paths may show no difference; that is an expected outcome, not a failure.

## 2. Facts from the exploratory LCC runs (not a substitute for the campaign)

- Taxol B3LYP/def2-SVP workflow: A100 35 s, V100 60 s (G1, cuTENSOR); G1 is about neutral vs G0 on speed with cuTENSOR, but needs 20 GB vs 30-55 GB.
- Without cuTENSOR (CuPy engine) G0 is 2.4x slower on A100 (85 s) and runs out of memory on a 32 GB V100; G1 is unchanged. On P100 (CuPy engine) Tamoxifen G0 32 s vs G1 13 s.
- J/K GEMMs are at about 85-90% of the cuBLAS DGEMM ceiling on A100 and V100; SCF cycle-count tricks give under 5% on large systems; grid build is about 0.1 s.
- In-place metric application cut the G1 gradient peak (Taxol 6.6 to 4.1 GB, valinomycin 14.8 to 8.7 GB) with identical numbers and 33 unit tests passing; its P100 verification was still running when this plan was written.
- P100 12 GB: G1 + host tier runs Taxol; P100 16 GB: valinomycin (before the in-place change).
- A100 node `ganode001` was shared with a long-running job during early runs: timings there are noisy and not to be reused.
- Setup lessons: Pascal needs its own LibXC (`named symbol not found` otherwise); helper-file edits invalidate a frozen campaign; the first sm70/80/90 build used the wheel LibXC.
- **The non-core adapters (Hessian, TD, MP2, CCSD, properties, optimization, solvent, periodic) exist but have never run on a GPU.** The only earlier GPU attempts were access probes that failed for lack of a device. Their capability on LCC is unknown.

## 4. Frozen inputs and variants

- **G0:** upstream `9af748a`, untouched Python. **G1:** the reviewed working tree at freeze time (including the in-place metric change). **CPU:** PySCF with matching model.
- **One unified native build** for all GPU strata: CUDA 12.4, architectures 60;70;80;90, LibXC 7.1.2 built from source for the same list (replaces the wheel LibXC and the separate sm60 tree, so one campaign hash covers every card and the CPU references are shared). Record compiler, driver, LibXC, CuPy and PySCF versions.
- **Engine** is an environment stratum recorded in every record: `cutensor` (default where installed) or `cupy` (`CONTRACT_ENGINE=cupy`). P100 uses `cupy` unless cuTENSOR is shown to run on sm60.
- **Settings** exactly as the broad plan: FP64, level-3 NWChem-pruned grid, conv 1e-10 / grad 1e-7, auxiliary and grid response, MINAO guess. Task-specific settings are fixed in `cases.json` (section 5.2).
- Per-card forks of one master campaign (identical `campaign.json`), shared CPU references; `CUPY_CACHE_DIR` per (engine, architecture); nothing in `$HOME`.

## 5. Experimental design

### 5.1 Part A: core SCF energy + gradient (60 cases)
- The 60 core cases, G0 and G1, on P100-16, V100-32, A100-80.
- Per case and card: one memory observation per variant (allocator hook, separate process), then 5 timing pairs in balanced AB/BA order (seeded); extend to 9 if either median absolute deviation exceeds 3% or the ratio lies in 0.95-1.05.
- A variant that fails the accuracy gate or is `resource_limited` stays in the record and is excluded from equal-accuracy ratios (known: G0 Taxol gradient fails the CPU gate).
- Pilot first: H2O, benzene TPSS, vitamin C, Taxol, OH wB97X probe, 3 pairs; OH is expected to be non-converged and is kept as such.

### 5.2 Part B: other QM job families (66 registry cases)

All use the same molecules/settings discipline as Part A (fixed geometries, hashed inputs, matched CPU model, fresh process, imports outside the timer). Gates are declared before any performance run and not loosened afterwards.

| Family (registry task) | Cases (IDs abbreviated) | Observable and gate | What G1 changes that could matter |
|---|---|---|---|
| Extra SCF energy+gradient (18) | wB97M-V (non-local correlation) on H2O, benzene, tamoxifen, vitamin C; ECP: CH3I, I2 (PBE); dispersion: D3BJ and D4 on H2O, tamoxifen; PCM (IEF-PCM) and SMD on H2O, inosine, tamoxifen, vitamin C | energy 1e-8 Eh, gradient 1e-6 Eh/Bohr; solvent: same model and cavity on CPU and GPU | DF/J-K/gradient/XC paths; solvent and dispersion add CPU or other stages |
| Hessian (8) | H2O, benzene, vitamin C with HF, PBE, B3LYP (vitamin C: PBE, B3LYP) | Hessian 1e-5 Eh/Bohr^2, symmetry, frequencies within 1 cm^-1 above 50 cm^-1 | DF integral storage and J/K derivatives (partly) |
| TDA (6) and TDDFT (6) | formaldehyde, benzene, inosine with B3LYP and wB97X, 5 roots | excitation energies 1e-6 Eh per matched root, oscillator strengths 5e-5, state matching | J/K builds in Davidson iterations (G1 touches `get_jk`) |
| DF-MP2 (4), DF-UMP2 (2) | H2O, benzene, vitamin C, water dimer; NO, OH (unrestricted) | correlation and total energy 1e-8 Eh each, frozen core off | DF integral storage (`df.py`) |
| CCSD (2, direct) | H2O, formaldehyde, cc-pVDZ | correlation and total energy 1e-8 Eh, residual recorded | none expected (no DF); a control for unaffected paths |
| Polarizability (3), NMR shielding (3) | H2O, benzene, vitamin C with B3LYP | polarizability 1e-5 au (finite-field cross-check); shielding 0.1 ppm, fixed gauge | SCF response; uncertain |
| Geometry optimization (4) | H2O, formaldehyde, benzene, vitamin C with B3LYP | both variants meet grms 1e-4 / gmax 3e-4 Eh/Bohr within 50 steps; CPU re-evaluation of both endpoints; endpoints compared, paths not assumed equal; separate replay of up to 10 archived geometries for per-step throughput | gradient (repeated) |
| Direct-SCF diagnostic (6) | H2O, benzene with HF, PBE, B3LYP, no density fitting | energy and gradient gates as Part A | different code path; separate lane, not in family averages |
| Periodic feasibility (4) | Si gamma, Si 2x2x2 k-mesh, Si supercell, MgO gamma (PBE, GTH-DZVP) | energy 1e-8 Eh per cell, forces 1e-6 Eh/Bohr where supported | none expected; feasibility report only |

Notes:
- The 12 `capacity` cases in the registry belong to the capacity study (section 7), not here.
- Families that depend on tasks that fail the capability gate (section 6) get one terminal status each (`unsupported`, `dependency_missing`, `accuracy_failed`, ...) and are listed in the coverage matrix; an unsupported task is never a speedup.
- Plan-level hypothesis to test, not assume: G1 is neutral on families that do not use its modified paths (CCSD, periodic) and may differ on those that do (SCF-based, TD, MP2).

### 5.3 Timing, memory and statistics for Part B
- Principal metric: complete-workflow elapsed time with task-specific boundaries (setup, ground state, task work, output conversion) declared in the manifest. Essential CPU stages (dispersion, ECP, cavity, geometry-optimizer driver) are included.
- 3 timing pairs initially; promote to 5 pairs (and to 9 under the noise rule) for any family cited in a headline claim. One memory observation per variant per case.
- Reported: per-family geometric mean of G0/G1 ratios over the shared qualified cases with the denominator and every excluded case listed. No cross-family average.

### 5.4 CPU timing lane
- Same workflow, fresh process, whole 48-core node, 48 threads (OMP/OpenBLAS/MKL), `--exclusive`, recorded CPU model and affinity.
- Part A anchors: 6 systems x 6 methods = 36 cases, 3 repetitions each.
- Part B: 3 repetitions for cases below about 300 AOs and 1 repetition (flagged) for expensive ones (for example vitamin C Hessian, inosine TDDFT, tamoxifen PCM/SMD). Single-repetition cases are labeled and not given ranges.
- CPU references (all 126 non-capacity cases) come from a Slurm array and are separate from CPU timing; reference runtimes are never used as CPU speeds.
- Reported as CPU / G0 / G1 side by side; CPU samples never enter G0-vs-G1 pairing (implemented and tested).

### 5.5 Engine strata and cold start
- On V100-32 and A100-80 only, repeat vitamin C, tamoxifen and Taxol (B3LYP, PBE), plus one Hessian and one TDDFT case, with `CONTRACT_ENGINE=cupy`, 5 pairs (3 for the families). Purpose: show the regime where the new code's speedup appears.
- One first-ever-process run per (card, variant, engine) with an empty kernel cache, reported separately (observed earlier: 15-20 s of run-time kernel compilation vs 3 s warm). Warm cache is the principal protocol.

## 6. Capability qualification gate (new; precedes any Part B timing)

For each family and each card (and each engine stratum used): run one tiny CPU/GPU case end to end (H2O or formaldehyde) through the actual adapter, and record the real classes and modules used, whether anything falls back to CPU, and the status label (`qualified`, `accuracy_failed`, `state_mismatch`, `nonconverged`, `unsupported`, `dependency_missing`, `resource_limited`, `timeout`, `infrastructure_failed`).
- A successful `to_gpu()` does not establish that the downstream task runs on the GPU; the record must name the implementing class.
- A family only enters timing when its tiny case is `qualified` on that card. Pascal-specific failures (kernels, LibXC, cuTENSOR) are expected to remove some families from P100 and are reported as such.
- Dependency skips (dispersion libraries, geomeTRIC, solvent extras) are recorded, never passed.

## 7. Capacity study (the interest in small-memory cards)

- Ladder from actual AO counts: vitamin C, tamoxifen, Taxol, valinomycin, `gly30`...`gly120`, water clusters nearest 1500/2500/4000 AOs; B3LYP/def2-SVP first, one def2-TZVP rung if the estimate fits.
- For each card (P100-12, P100-16, V100-32, A100-80, optional V100-16) and each of G0, G1: storage tiers GPU-resident, host RAM, disk (G1 only; 4 GiB staging, no cache). Record completion, workflow time, tracked GPU peak per phase, host RSS, scratch use.
- Stop climbing after two consecutive resource-limited rungs per (card, variant, tier). Largest completed AO count is the headline.
- Accuracy: full CPU reference where feasible; otherwise a capacity observation with finite checks (J/K cross-check, selected finite-difference forces), labeled as such.
- Hybrid tier (part resident, rest streamed) is a candidate optimization, not part of this campaign unless implemented first.

## 8. Required harness work before launch

1. Unified sm60-sm90 native build and LibXC (section 4); re-run unit tests.
2. Run the capability gate (section 6) for all adapters; fix adapter bugs found there (expect some: the adapters have only run on CPU fixtures). New tests for anything fixed.
3. Re-freeze: helper edits (CPU timing lane, scheduler admission policy) invalidated the old frozen campaigns; create a fresh master after all code edits, then forks per card. No edits to `qm_suite/*.py` or `gpu4pyscf/` after freeze.
4. Scheduler: GPU label and `--exclusive` option in the Slurm wrapper; capacity lane (currently `NotImplementedError`); keep device-memory admission advisory on dedicated cards; extension lanes use 3 pairs.
5. Aggregation: combine per-card summaries into CPU / G0 / G1 tables with engine and family as columns; add co-tenancy snapshot (`squeue -w node`, GPU utilization before/after) per job.
6. Code review of the G1 diff (including the in-place change) before freeze.

## 9. Execution order and rough cost

Estimates from the measured workflows above and general expectations for these job types; they are budgets, not predictions, and Part B costs have no GPU measurements behind them yet.

| Phase | Work | Rough cost |
|---|---|---|
| 0 | Build, tests, review, freeze, dry run | 1 day of attention, 1 CPU-node hour |
| 1 | Capability gate (tiny cases, all families, 3 cards) | under 1 GPU-hour per card, plus adapter fixes |
| 2 | CPU references for 126 cases (Slurm array) | about 45-80 node-hours in parallel; Hessian, TDDFT, CCSD and PCM/SMD on larger molecules dominate, with a 4 h cap per job |
| 3 | Pilot (5 core cases + one case per family, 3 cards) | about 2-3 GPU-hours per card |
| 4 | Part A core 60 on each card | about 8-15 GPU-hours per card |
| 5 | Part B 66 cases on each card where qualified | about 8-12 GPU-hours per card (guess) |
| 6 | CPU timing (anchors + Part B) | about 40-60 node-hours |
| 7 | Engine strata and cold start | about 3-4 GPU-hours per card |
| 8 | Capacity ladder | about 10-20 GPU-hours per card, dominated by disk-tier runs |
| 9 | Audit, tables, figures, report | after all phases |

Cards run in parallel; wall time 4-7 days if queues allow. Slurm limit is 3 days per job; the scheduler resumes from immutable records.

## 10. Risks

- Queue wait on the few P100-16 nodes; P100 driver or toolkit incompatibilities (cuTENSOR on sm60 untested); some families may not run on Pascal.
- Adapter or library bugs in never-executed families; non-converging or slow CPU references (a 4 h cap turns them into `timeout`, not silent omissions).
- Shared nodes make timings noisy: mitigate with `--exclusive`, co-tenancy records and median/MAD reporting.
- A unified LibXC build changes the LibXC version relative to earlier exploratory runs: all claims come from the campaign only.
- Disk timings depend on page cache and filesystem load: label cache-dependent.
- Cases that do not converge or whose G0 fails accuracy are results, not defects; gates are not loosened after seeing them.
- Several families (Hessian, TDDFT, solvent, optimization) route through different code than SCF+gradient, so the exploratory speed and memory findings may not transfer; report separately.

## 11. Decisions needed from the user

1. CPU timing scope: Part A anchors only (36) or all 60? Part B CPU repetitions: 3 for small and 1 for expensive cases as proposed, or 1 everywhere?
2. `--exclusive` nodes for the timing lane (cleaner, longer queue) or shared with co-tenancy records?
3. Include V100-16 and P100-12 beyond the capacity study?
4. Build the hybrid host/GPU tier before the capacity study, or measure host-only first?
5. Which Part B families matter most? If budget is tight, my suggested priority is: extra SCF (solvent, wB97M-V, ECP, dispersion), Hessian, TDA/TDDFT, optimization, DF-MP2, then properties, CCSD, direct SCF, periodic.
